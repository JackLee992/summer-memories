# 传统动画经验如何用于横版动作游戏

调研日期：2026-09-20。范围：公开资料阅读与现有实现检查；开发继续暂停，不安装软件、不生成新素材、不制作动画。本文区分官方资料中的方法与对本项目的建议，尚无新管线的实际成本测量。

**结论：可以借鉴，最值得借鉴的是先设计运动、再完成画面的顺序，以及复用一致角色部件的方法。** 传统逐帧动画本身需要大量绘制和修正，不会天然便宜。对于当前成本约束，优先候选是“少量确认过的关键姿势＋2D 骨骼/部件复用＋特殊姿势替换”的混合方法，而不是继续批量生成独立姿势图。

## 传统动画怎样保证连续性

Toon Boom 的官方传统流程包括角色/道具设计、模型设定包、分镜与定时预演、关键姿势、动画、线稿试播、摄影表、清稿、上色和合成。[S1] 不同工作室的分工有所不同；原画、中间画、清稿可能由一人或不同部门完成。

| 方法 | 实际控制的内容 | 对当前问题的启发 |
|---|---|---|
| 角色与道具设定表 | 人体比例、服装、多个角度和武器尺寸 | 日鹤锤头、柄长、握点须先固定；新姿势不能重新发明它们 |
| 关键姿势 | 动作意图、重心和主要轮廓 | 先确定扛肩、蓄力、挥出、命中、收招，暂不追求精美上色 |
| 过渡关键姿势（breakdown）与中间画 | 从一个姿势到另一个姿势所走的路线 | 锤头走什么弧线、肘部怎样绕过躯干，需要设计，不能平均混合两幅图片 |
| 摄影表/时间表（X-sheet） | 哪一幅画从何时出现、保持多久 | 蓄力、命中和收招有不同节奏；图片张数不等于动作时长 |
| 透台/洋葱皮与翻页检查 | 比较前后画的形体、位置和轮廓变化 | 及时发现身体忽大忽小、脚底漂移、武器长度变化 |
| 线稿试播（line/pencil test） | 正常速度下是否真的成立 | 运动未通过之前不进入昂贵清稿和上色，降低返工 |
| 先主体后附属动作 | 先躯干和腿，再头、手臂、衣物等 | 先让人体运动连贯，再处理潮的头发和裙摆 |

其中粗稿优先、前后图叠加参考、逐张翻看、播放通过再清稿，均可在官方纸上动画的数字化教程中直接核实。[S2] “加更多帧”只有在造型、轨迹与节奏已成立时才有帮助。

以日鹤重锤为例，可先在同一张画布中画出几个粗略关键姿势，标记脚底接触点、骨盆、双手握点和锤头位置。先检查重心转移与挥锤弧线，再补过渡姿势。挥出的速度与收招时间不必对称；头发和衣摆可延后跟随。这是动作设计建议，不能把某个固定帧数当成重锤动作的通用标准。

动画中的绘图更新频率也不等于游戏刷新频率。例如在 24 fps 时间线上，一张画保持两帧意味着该段每秒至多使用 12 张不同图；这只是时间分配示例，不是所有动画片或所有动作的规范。游戏输入、移动和碰撞仍可按游戏自身的更新节奏处理，不必因为画面采用停格而变迟钝。

## 节约重复劳动的做法

Toon Boom 的 cut-out（部件/数字偶动画）流程强调资产复用：将统一角色拆成部件，设定层级与旋转中心，建立可复用素材库，再制作动作；同时明确，某些场景混合手绘动画能提高效果。[S3]

这为本项目提供了一条候选路线：把头、躯干、四肢、前后头发、裙摆、武器分开，使用骨骼控制位置，手型和特殊角度换图。日鹤的锤子作为独立刚性部件，避免每张图重新生成后长度变化；潮的头发拆成主束，用少量关键姿势控制弯曲，大幅变形或攻击轮廓再补画。

这条路线有明确限制：被身体挡住的部位需要补全，肘膝和肩部不能像纸片机械旋转；转身、透视缩短、手臂交叉、双手握锤及强烈挤压拉伸通常需要额外视图或替换图。现有整张 PNG 抠出透明背景，不等于已经拥有可绑定的分层角色。

| 路线 | 主要成本 | 当前适用判断 |
|---|---|---|
| 完整手绘逐帧 | 每个动作的原画、中间画、清稿、上色与返修 | 上限高，当前不宜一次覆盖全角色全动作 |
| 2D 骨骼/部件复用＋特殊帧 | 前期拆层补图、绑定、动作设计，后续复用 | 最值得小样验证；预期减少重复绘制，尚未实测节省比例 |
| AI 视频 → 抽帧/修帧 | 生成重试、选取可用运动、稳定形体、去背景、修接缝 | 可当运动参考，直接作为游戏资源是否省钱仍不确定 |
| 独立 AI 姿势图 → 自动插帧 | 结构不一致带来的大量修补 | 当前已有衔接失败，不建议继续扩大批量 |
| 3D 动画 → 固定机位渲染 2D | 建模、绑定和动画维护 | 能保证共享骨架，但会重新引入用户已认为过重的前期成本 |

Unity 6.0 官方手册确认 2D Animation 提供精灵骨骼动画工具及运行时组件。[S4] 当前工程 `Packages/manifest.json` 尚未声明该包，也未验证接入。可以继续使用现有 Unity 6000.0.83f1；这次没有安装或更换任何工具。官方包详细页本次浏览被客户端阻止，因此不对具体包内功能逐项作已验证声明。

## 游戏还要额外解决动作之间的衔接

动画片播放顺序预先确定，游戏则会遇到玩家随时松开移动、转向、出招、受击或切人的情况。以下为针对当前工程的设计推论：即使一段跑步自身流畅，也还要设计它与待机、起跳、攻击之间怎样衔接。

检查 `SideWorld.cs` 可见，当前跑步使用全局时间轮换四张图；轻击、重击、技能共用三张姿势，并按动作时长比例切换。`prepare_side_sprites.py` 中还有重复姿势和日鹤武器合成。由此可见，问题同时来自素材与播放逻辑：

- 跑步进入时可能落在任意循环相位，尚未专门处理起步和停止。
- 不同攻击需要各自的蓄力、命中、收招时间表，不能只复用同一组三张图。
- 脚部接地应与角色位移一致，避免滑步；武器画面与命中窗口需一起校准。
- 应单独检查“待机→跑步→停止”“跑步→跳跃→落地”“攻击→受击/切人”等衔接。
- 两张姿势不同的整幅精灵做透明渐变会出现重影；骨骼插值也需要合适的姿势和节奏，不是自动解决动作表演。

因此后续验收要分成造型一致、动作内连续、动作间连续、操作反馈四项，不能只检查图集是否成功导入。

## AI 适合承担的位置

AI 可用于探索角色设计、提供动作参考、生成候选关键姿势、辅助局部修图；本地抠图工具可以继续处理背景。但已经确认的动作骨架和武器几何关系，应作为约束保留下来，避免每一帧重新自由生成整个人物。

Seedance 可以尝试生成连贯动作参考，帮助观察重心与发力顺序；本次没有生成、也没有验证其当前可用率。参考视频仍需检查人体与武器一致性，且不等于可直接驱动角色的动作捕捉数据。光流/AI 插帧也无法可靠替代对遮挡关系、握持和运动轨迹的设计。

若恢复制作，建议先只验证“日鹤扛肩→蓄力→挥锤→收回待机”一个动作。先粗稿/骨骼预演，再做少量清稿和游戏内对照；记录准备、制作、返修的实际时间、生成费用及可用结果。只有正常速度下不跳形、握点稳定、锤子比例一致、动作首尾能接上、命中节奏清楚，才考虑扩展到跑步与其他人物。这个小样目前只是建议，开发仍暂停。
